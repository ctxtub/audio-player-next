# E2E 测试规范与执行治理全景指南（README.md）

本文档是本仓库端到端（E2E）测试体系的**唯一权威规范入口（Canonical Entrypoint）**。所有 E2E 测试规格、执行标准、架构隔离设计及用例索引均以此为准。

> **核心资产边界铁律**：
> - **Git 追踪资产**：`docs/e2e/` 下的测试用例规范、调度拓扑、隔离架构与执行标准是本仓库的单一事实来源（SSOT），必须伴随业务代码变更同步维护并纳入 Git 版本控制。
> - **本地私有资产**：所有测试运行过程中产出的截图（`ui-*.png`）、请求响应与网络记录（`network.json`）、控制台输出（`console.json`）、音频探针快照（`audio.json`）、数据库快照（`db.txt`）、运行报告（`report.md`）以及用例结果映射表，**严禁提交入库**，统一留存在 `.e2e-results/` 与 `.e2e-runtime/` 中（已被根目录 `.gitignore` 完全忽略）。

> **治理与调度状态说明**：
> 1. **执行模式**：单一全局串行 DSH 执行队列，严格遵循套件顺序 `01 → 02 → 03 → 04 → 05 → 06` 连续编号执行（共 58 项自动化原子单元）。
> 2. **人工排除项（manual_excluded，1 项）**：`E2E-06-08`（bfcache 恢复探针）为人工探索性验证，移出自动化调度。
> 3. **结果隔离与准入保护**：执行结果保存在本地私有目录 `.e2e-results/`（Git 忽略），已获完整证据与终态验证的通过项受到准入保护免于冗余执行。

## 7. 单元测试执行规范（Unit Test Standard）

1. **执行职责与范围**：
   单元测试位于 `tests/` 目录下，负责对服务端核心工具函数、权限矩阵、数据迁移事务回滚逻辑、进度单调算法及限流算法进行快速纯内存/隔离库验证。
2. **执行命令与准入要求**：
   - 统一执行命令：`yarn test`（实际由 `node scripts/run-tests.mjs` 调度 jiti 执行）。
   - 涵盖套件：
     - `tests/test-sec-01.ts`、`tests/test-sec-02.ts`（安全守卫）
     - `tests/test-batch-02.ts`、`tests/test-release-pipeline.ts`（发布流水线）
     - `tests/test-auth-guest-matrix.ts`（身份矩阵）
     - `tests/test-rate-limit.ts`（限流阈值）
     - `tests/test-orphan-prevention.ts`（防孤儿回滚）
     - `tests/test-guest-config.ts`、`tests/test-guest-creative-sync.ts`、`tests/test-guest-creative-e2e-harness.ts`
     - `tests/test-paragraph-resume.ts`（段落断点）
   - **门禁要求**：代码提交前必须达成 `ALL TEST SUITES PASSED SUCCESSFULLY (exit code 0)`，并与 `yarn lint`、`yarn tsc --noEmit`、`yarn build` 并列作为四道硬门禁。
3. **隔离约束**：
   单元测试严禁依赖外部网络或公网大模型，测试数据通过内存或临时 SQLite 测试库生成，用毕即销毁。
   合成 fixture 资产索引见 [fixtures.md](./fixtures.md)（`tests/fixtures/`，Git tracked；
   隔离库口径 SSOT：`setupIsolatedDb`，禁依赖 `prisma/dev.db` 回退）。

## 8. E2E 隔离执行规范（E2E Execution Standard）

执行 E2E 测试时，必须严格遵守 [execution-isolation.md](./execution-isolation.md) 中规定的隔离执行准则：

1. **环境与端口隔离铁律**：
   - **严禁触碰生产环境**：严禁连接生产数据库（Docker 生产路径 `/app/data/app.db`、生产端口 38080）；严禁使用共享开发库 `prisma/dev.db`。
   - **隔离执行端口**：测试服务统一运行在隔离端口 `31111`（`yarn dev -p 31111`）。
   - **隔离数据库**：测试数据库必须指向仓外临时库 `.e2e-runtime/e2e.db`（`DATABASE_URL=file:.e2e-runtime/e2e.db`）。
   - **本地 Mock 上游**：LLM 与 TTS 请求必须全部指向本地 Mock 服务 `http://127.0.0.1:9301/v1`（通过 `OPENAI_BASE_URL` 注入），严禁外联真实 OpenAI API。
2. **凭据安全与脱敏**：
   - 测试账号、密钥口令只存在于本地未入库的 `.e2e-runtime/.env.e2e` 中。
   - 规范与代码库中一律使用符号标识符：`{{E2E_USER_A}}`、`{{E2E_USER_B}}`、`{{E2E_PASS_A}}`、`{{E2E_SESSION_SECRET}}`。任何真实密码密钥严禁进入 Git。
3. **DSH 调度治理与 Worker Mock 生命周期契约**：
   - **全局单一活跃 Worker**：任何时刻全局仅允许启动 1 个 DSH Worker，严禁并发派发。
   - **显式 3 小时安全时限**：启动任务显式配置 `--timeout 10800`，杜绝因默认超时导致进程中途被杀。
   - **Worker 自主托管 Mock 生命周期（核心执行契约）**：
     - 测试前检测 9301（`ss -ltn | grep -q ":9301 "`）；若缺失则以项目真实本地启动器启动：
       `(set -a; [ -f .e2e-runtime/env.e2e.sh ] && source .e2e-runtime/env.e2e.sh; set +a; nohup node .e2e-runtime/mock-openai.mjs > .e2e-runtime/mock.log 2>&1 & echo $! > .e2e-runtime/mock.pid)`；
     - 记录 PID（`.e2e-runtime/mock.pid` 与局部变量 `MOCK_PID`），明确生命周期所有权；
     - 有界轮询健康检查（上限 10 秒，每 0.5 秒轮询一次，端点 `POST http://127.0.0.1:9301/v1/chat/completions`）；
     - 启动失败判定：若超时未健康响应直接判为 `UNVERIFIED` 并退出，严禁推进后续断言；
     - 流量与环境：上游流量仅定向至 `http://127.0.0.1:9301/v1`；持续保留 31111 应用服务与测试数据库 `.e2e-runtime/e2e.db`，严禁重启应用或删除数据库；
     - 测试后清理：测试完成后仅清理当前 Worker 启动的 Mock 进程（从 `.e2e-runtime/mock.pid` 读取 kill 并清理文件）；绝对不得关闭既有 9301 监听；31111/DB 严禁变更。
   - **终态门禁与证据留档**：每个原子单元执行必须以合规 `report.md`、关键证据写入盘中、终端显式给出 VERDICT 后以 exit 0 退出，方可推进下一用例。
   - **503/429 弹性退避**：捕获 503/429 错误时强制静默等待 60 秒，重试 ≤ 3 次。
   - **准入通过项保护**：已通过终态验证与完整证据核验的用例受到保护，免于重复执行。
4. **证据与结果私有边界**：
   - 执行产生的全量截图、HAR 日志、DB 导出与运行报告只能写入 `.e2e-results/`。
   - 运行产物绝对不进入 Git。执行前后运行 `git status --porcelain`，除预先授权的规范文件外必须保持工作区干净。

## 9. 测试资产维护规范与变更流程（Maintenance Standard & Change Process）

为了保证测试资产的长期健康与可维护性，所有协作者与 AI Agent 必须遵循以下维护流程：

1. **规范驱动开发（SDD）双向联动**：
   - 当新增功能、修改 UI 交互、调整 API Schema 或改变状态机时，必须在对应的功能套件（`01-` 到 `06-`）下新增或更新相应的用例规范文件。
   - 禁止在业务代码改动后留下过时失效的测试用例；禁止在用例规范未同步更新的情况下声称任务完成。
2. **规范文件与命名准则**：
   - **文件命名**：套件目录下必须以两位数字序号开头，格式如 `01-用例名称.md`。
   - **ID 编码**：统一使用规范纯数字 ID `E2E-XX-YY`（父用例）或 `E2E-XX-YY-ZZ`（原子单元），**严禁使用任何非规范前缀或别名**。
   - **自包含与确定性**：每份规范必须包含完整的前置条件、清晰的操作步骤、逐层断言（UI/音频/网络/DB）、清理规范与代码溯源（`file:line`）。
3. **变更审计与质量门禁**：
   任何测试规范变更必须在提交前通过确定性审计：
   - 链接有效性：`README.md` 中所有引用链接必须能够正向解析。
   - 覆盖保全性：58 个父用例与 54 个串行原子单元的覆盖面不得丢失。
   - 命名纯洁性：规范主属性与标题统一采用纯数字规范 ID。
   - 边界合规性：核对 `.gitignore` 确保结果目录不被意外跟踪。

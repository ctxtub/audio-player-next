## 0. 摘要与非目标

### 0.1 为什么做

现行三处规则文本均为"单工作区单写者"。翔哥已拍板放宽为**条件化多写者**：评估影响面之后，
只要并行写者不是修改同一个文件、做的事情是分割的、独立的，就允许派多个。

放宽不是去掉约束：原规则实际在防 5 件事，其中三件与"文件是否相交"无关，
所以规则不能只写"不碰同一文件"，必须把 5 条风险的对策逐条写进正向流程。
本规范是该决策的 dated 记录，也是三处规则文本措辞的唯一依据。

### 0.2 非目标（明确不做）

1. 不改任何产品代码行为、路由、鉴权、播放、同步语义；`docs/e2e/**` 语义权威不动。
2. 不改生产数据/端口隔离（`docs/testing/execution/isolation.md`）、DB 单写与并发写禁令、
   broad-kill/rm 禁令、push/merge/deploy/Actions 需授权、只读 review 的只读性。
3. 不做远端写入：不 push、不 merge、不 rebase、不把本分支合回主分支；落地需另行授权。
4. 不改 `tests/**`、`scripts/**`、`docs/testing/**`；如别处需同步措辞，只在报告里建议，不动手。
5. 不重写已发布历史文档；本 spec 为新增快照，落盘后只更新状态或追加勘误。

## 1. 决策与依据

### 1.1 决策（翔哥原话要点）

- 「评估影响面之后，只要他们不是修改同一个文件、做的事情是分割的、独立的，就允许派多个。」
- 三个关键词：**先评估影响面**、**不相交路径所有权**、**任务相互独立**。三者缺一不可。

### 1.2 影响面评估：原规则在防的 5 件事（ROBOT 已完成，本节为其落字）

| # | 风险 | 与"文件是否相交"是否有关 | 对策（规则必须包含） |
|---|---|---|---|
| 1 | **执行器的工作区独占锁（决定性约束）**：`dshctl start` 按 canonical CWD 取**非阻塞独占锁**，同一工作区的第二次派发直接失败（`Workspace '…' is locked by an active run`）。实现位于 vendored runner（`dshctl` 第 379/576 行），设计意图是"同工作区绝不重复劳动"。 | 无关 | **DSH 多写者必须走独立 worktree（路径 A）**；规则如实写明这一层，否则规则无法执行 |
| 2 | **共享 git 暂存区**：同一工作树只有一份 index。A 暂存 → B 暂存 → A 提交 ⇒ A 的提交混入 B 的半成品。 | 无关（同树即有） | **只用显式路径提交**（`git add <paths>` / `git commit -m … -- <paths>`），永不依赖 index 现状；独立 worktree 模式下该风险天然消失，但同一工作树并行场景仍须遵守 |
| 3 | **"tracked 树须干净"的前置门**：L3 快照守卫（WS4）在有未提交改动时直接拒绝；多写者会让树长期为脏，等于把 L3 门对所有写者关闭。 | 无关 | **此类门只在相关写者静默时运行** |
| 4 | **共享重套件资源**：浏览器快照锁、隔离库、端口为共享资源；两个重跑即使在不同 worktree 仍可能争用（快照目录 `.e2e-runtime/` 虽在各自 worktree 内，但机器资源与端口池有限）。 | 无关 | **重套件串行**；并发的写者把"跑重套件"排到互不重叠的时间窗 |
| 5 | **误带走他人物件**：`git add .` / `-A` / `commit -a` 会把他人半成品或证据文件卷入提交。 | 部分相关 | **禁用这三者，只显式路径提交** |

结论：只写"不碰同一文件"是不够的。新规则 = 不相交路径所有权 + 上表 5 条对策中可执行的部分
（第 1 条决定路径选择，第 2/3/4/5 条写成正向流程）。

## 3. 新规则全文

### 3.1 两条路径

**路径 A · 独立 worktree 多写者（DSH 并行的唯一可行方式）**

- 每个写者各自独立 worktree + 分支，天然隔离 index、tracked 树与运行时目录。
- 事先声明不相交路径所有权；任务相互独立。
- 落地（merge/land）需显式授权；未获授权不得合回主分支。
- 仓库已有先例：`w2a`–`w2d`、`testplan-p1..p4`、`testrev-t1..t4` 等。
- **DSH 走路径 A**，因为 `dshctl` 对 canonical CWD 持非阻塞独占锁，
  同一工作树内的 DSH 多写者在派发时即失败，无法执行。

**路径 B · 非 DSH 的同一工作树并行**（如人工 + 单一 Agent 并存）

允许，前提是同时满足：

1. (i) 事先声明不相交路径所有权；
2. (ii) 只用显式路径提交（`git add <paths>` / `git commit -m … -- <paths>`），永不依赖 index 现状；
3. (iii) 重套件串行，跑重套件的时间窗互不重叠；
4. (iv) 需要干净 tracked 树的门只在相关写者静默时跑；
5. (v) 仍禁 `git add -A` / `git add .` / `git commit -a`。

### 3.2 仍然禁止清单

- 未获明确授权不得 push、merge、deploy、触发 Actions、reset、rebase、force 或修改生产状态。
- 落地（merge/land）需显式授权。
- `git add -A` / `git add .` / `git commit -a` 始终禁用。
- 生产数据/端口隔离、`docs/testing/execution/isolation.md` 的隔离路径与端口、DB 单写与并发写禁令、
  broad-kill/rm 禁令保持原样。
- 实现者不得自批，验收者不得顺手修实现；实现、review/acceptance、发布必须是不同会话。
- 只读 review 不得起服务、清进程、改 tracked 实现。

## 4. 如何判断一次并行是否安全（可执行检查清单）

按序执行，任一步答"否"即停止并行，改串行或重新切分：

1. **评估影响面**：列出各写者的目标文件集合与运行时需求（是否跑重套件、是否需要干净 tracked 树）。
2. **路径所有权不相交**：各写者的授权路径两两不相交，并写入各自会话的 change manifest。
3. **任务相互独立**：各写者的验收标准可独立验证，不依赖对方的半成品。
4. **选路径**：DSH 派发一律走路径 A（独立 worktree）；非 DSH 的同树并存走路径 B 并满足 (i)–(v)。
5. **提交方式**：确认所有写者只用显式路径提交，禁用 `add -A` / `add .` / `commit -a`。
6. **重套件调度**：确认重套件串行，时间窗互不重叠。
7. **干净树门调度**：确认需干净 tracked 树的门只在相关写者静默时运行。
8. **落地授权**：确认合并/落地已获或待获显式授权；未获授权前各写者只在各自的分支出提交。

# 首篇自动播放过渡与输入解锁计划

状态：已实施；静态门与生产构建通过，浏览器旅程因 runner 的 clean-tree 门禁待提交后复验

## 目标

- 首篇作品晋升为正式 Work 后，到自动播放真正起播前，作品卡持续显示“正在准备语音”且不可点击。
- 同一 Work 的自动播放与用户操作不能并发进入音频准备或重复驱动 Transport。
- 文本生成与消息交付完成后立即解除输入区提交锁；后续保存、语音准备和自动播放不继续占用“发送中”状态。

## 非目标

- 不改变后续作品的手动播放语义。
- 不改变连续创作下一篇的独立准备和续播状态机。
- 不改变 StoryAudioAsset 的服务端租约、缓存或合成协议。

## 方案

1. 增加一个只表达“首篇自动播放已承诺”的轻量客户端意图 Store，以消息 ID 绑定目标卡片。意图在生成开始前登记，在自动播放完成、失败、中断或新流抢占时按身份清除。
2. 卡片 ViewModel 在该意图命中时优先派生为 `preparing`，复用现有 loading 文案、spinner 和禁用态。
3. 将首篇自动播放编排从 `beginChatStream` 的返回值中拆出为受代次保护的后台任务，使 Composer 的本地提交锁只覆盖真实消息流。
4. 正式播放入口区分用户按钮和自动播放来源：自动播放遇到同一 source 恒为幂等 no-op；用户按钮在 `hydrating`、`synthesizing` 和尚未出声的 `playing` 状态也不重复执行 `playParagraph`。

## 验收标准

- 首篇卡片在自动播放准备窗口不出现可点击的“播放”。
- 自动播放准备中重复调用同一 Work 播放入口不会再次 resume、合成或播放。
- 消息流结束后输入框与“新建创作”恢复可用，不等待 TTS 或自动起播完成。
- 自动播放成功后卡片正常进入“暂停”；失败后显示既有错误态并允许重试。
- `yarn test:fast`、`yarn build`、`git diff --check` 通过。

## 风险与回退

- 后台自动播放必须继续使用 `streamSeq` 和消息身份守卫，避免新建创作或新消息后旧任务复活。
- 意图清理采用 compare-and-clear，旧任务不得清除更新消息的意图。
- 若自动播放失败，清理意图后由 PlaybackSession 的 `error` 状态接管卡片展示。

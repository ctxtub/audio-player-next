# E2E 测试资产维护规范与变更规则（MAINTENANCE.md）

本文档定义本仓库端到端（E2E）测试体系的维护规范、用例演化标准与质量审计门禁。所有协作者与自动化助手均须严格遵守本文档所载规则。

---

## 1. 规范驱动开发（SDD）双向联动

1. **规范优先与同步更新**：
   - 凡涉及页面渲染、用户交互、API Schema 变更、鉴权守卫或状态机调整的代码修改，均须在对应的功能套件（`01-` 至 `06-`）下同步更新或新增用例规范。
   - 严禁在业务代码改动后留下失效或不一致的用例规范。
   - 严禁在用例规范未完成同步更新与核验前声称任务完成。

2. **单一事实来源（SSOT）**：
   - `docs/e2e/` 下的规范文件为系统行为断言的权威依据。
   - 实现代码若与用例规格产生分歧，须以产品契约与用例规格为基准进行对齐与澄清。

---

## 2. 规范文件结构与编号准则

1. **套件与目录组织**：
   - 套件目录统一采用两位数字前缀与功能命名：
     - `01-基础冒烟与页面基线`
     - `02-交互并发与竞态防御`
     - `03-播放状态与内核一致性`
     - `04-云端存储与多端数据调和`
     - `05-认证授权与会话生命周期`
     - `06-异常处理与接口限流`
   - 规范文件名以两位数字序号开头，格式如 `01-用例名称.md`。

2. **规范 ID 编码规范**：
   - 父用例统一使用纯数字大写规范 ID：`E2E-XX-YY`（其中 `XX` 为套件编号 `01`..`06`，`YY` 为用例序号 `01`..`12`）。
   - 原子执行单元在父用例 ID 基础上扩展两位序号：`E2E-XX-YY-ZZ`（如 `E2E-01-06-01`、`E2E-01-06-02`）。
   - 严禁使用任何非规范前缀或别名。

3. **单用例规范要素完备性**：
   每份用例规范文件必须具备以下完整要素：
   - **元数据表格**：规范 ID、所属功能套件、规范层级、优先级（P0/P1/P2/P3）、自动化类型（`AUT-BROWSER`、`AUT-API`、`AUT-NODE`、`MANUAL`）、执行调度阶段。
   - **用例规格**：
     - 前置条件与数据夹具（使用统一符号标识符如 `{{GUEST_FRESH}}`、`{{E2E_PORT}}`）。
     - 清晰的操作步骤序列。
     - 逐层断言：UI 断言、音频/浏览器断言、网络/数据断言。
     - 用例级清理要求。
     - 证据要求（指定必须产出的证据文件名）。
     - 代码溯源（指向具体的源码路径与行号）。

## 3. 执行环境隔离与私有边界

1. **环境与数据绝对隔离**：
   - 严禁触碰生产环境与生产数据库（Docker 生产路径 `/app/data/app.db`、生产端口 38080）。
   - 严禁使用共享开发库 `prisma/dev.db`。
   - 测试服务统一使用隔离端口 `31111`，数据库指向 `.e2e-runtime/e2e.db`。
   - 外部 LLM 与 TTS 服务统一指向本地 Mock 服务 `http://127.0.0.1:9301/v1`。

2. **凭据安全脱敏**：
   - 真实凭据、密钥与测试密码严禁进入 Git 跟踪范围。
   - 规范文档与代码中统一使用符号占位符（如 `{{E2E_USER_A}}`、`{{E2E_PASS_A}}`、`{{E2E_SESSION_SECRET}}`）。

3. **运行产物私有化**：
   - 执行产生的所有截图、控制台日志、网络拦截记录、数据库快照及运行报告仅留存于本地 `.e2e-results/`。
   - 根目录 `.gitignore` 确保结果与运行时文件永不被提交入库。

---

## 4. 调度治理与终态准入铁律

1. **共享测试环境单一执行 Worker**：
   - 同一 Git 工作区及同一 `.e2e-runtime` / `.e2e-results` 结果根在任何时刻仅允许 1 个 E2E 执行 Worker，严禁重叠启动服务或写证据。
   - 固定同一 target SHA 的只读调研与 review 可以并行，但不得修改文件、启动服务或清理进程；独立 worktree 只有在显式分配独立 runtime/results 根和所有权后才能并行执行。

2. **执行时限与弹性退避**：
   - 任务启动显式配置超时时限 10800 秒。
   - 遇 503/429 错误时强制静默退避 60 秒，单任务重试上限 3 次。

3. **终态门禁与通过项保护**：
   - 用例执行完成必须在终端输出确定性 VERDICT，并生成包含全部断言证据的 `report.md`。
   - 具备完整有效终态证据与通过判定的用例受准入保护，调度队列仅调度待执行或未决项。

---

## 5. 变更审计标准

在对测试规范与资产进行任何修改时，必须通过以下确定性审计门禁：

1. **规范完整性**：保持 59 个父场景文件与 62 个原子 case 的完整覆盖（H-21 一拆二后），不得遗漏功能路径。数量口径唯一以 `yarn test:static`（checker）输出为准，本文件不手维护第二份总数。
2. **链接有效性**：`docs/e2e/README.md` 中全部引用链接与锚点必须能够正确解析。
3. **命名规范性**：全量规范文件与属性严格遵循纯数字规范 ID。
4. **工作区整洁性**：执行审计前后确认 Git 状态未受临时产物或私有结果污染。
